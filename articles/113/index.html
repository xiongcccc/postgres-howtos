原作者：Chris van Eijk，Now-Next。原文发表于 2026 年 11 月 2 日：server closed the connection unexpectedly in PostgreSQL。

以下为原文翻译，文中的“我们”及实验数据均指原作者及其测试。

在六种客户端中实测 PostgreSQL 的 server closed the connection unexpectedly：不同原因在服务端日志中留下什么，原因信息去了哪里，以及 COMMIT 结果如何变得不确定。

“server closed the connection unexpectedly” 是什么意思？

server closed the connection unexpectedly 表示客户端库 libpq 发现连接已经断开。这段文字并非 PostgreSQL 服务端发送，没有对应的 SQLSTATE，也没有说明原因：无论是 kill -9、OOM 杀进程、停库、超时、连接池代理退出，还是网络重置，我们都得到了同一句话。原因通常在服务端日志中。如果对应时刻的日志里什么都没有，就需要检查 PostgreSQL 之外的环节，或者确认 PostgreSQL 本身是否被杀掉了。

原因 服务端日志中的内容 处理建议
pg_terminate_backend() FATAL: terminating connection due to administrator command（57P01） 查明是谁执行了它；重新连接
快速关闭、docker stop、docker restart received fast shutdown request，随后各会话出现上述相同的 FATAL 重启后重新连接；服务恢复后，启用了 pre-ping 的连接池可以屏蔽这次断连
idle_session_timeout FATAL: terminating connection due to idle-session timeout（57P05） 让池中连接在达到该空闲超时前被回收，或调大超时
idle_in_transaction_session_timeout FATAL: terminating connection due to idle-in-transaction timeout（25P03） 不要让事务长时间保持打开状态
transaction_timeout（17 和 18） FATAL: terminating connection due to transaction timeout（25P04） 缩短事务，或调大超时
当前会话或其他会话的后端进程被杀死、崩溃 server process (PID 240) was terminated by signal 9: Killed；18 中写作 client backend (PID 213) was terminated... 如果有 DETAIL，查看它；对于空闲后端，它显示最后一条查询。查明是谁发送了信号
OOM killer 如果它选中的是后端进程，日志与上述 signal 9 完全相同，不会出现 OOM 字样 检查内核或容器，见下文
立即关闭 received immediate shutdown request 使用快速关闭；立即关闭会在下次启动时进行 WAL 回放
整个数据库服务器被杀死（docker kill -s KILL） 当时没有日志；重启后出现 database system was not properly shut down 检查宿主机或编排系统
PgBouncer 关闭客户端连接 PostgreSQL 没有相应日志，后端仍然存在；PgBouncer 日志为 closing because: client_idle_timeout (age=2s) 调大连接池代理的超时，或重新连接
网络重置 如果只有客户端收到重置，服务端没有日志；如果重置到达服务端，则记录 could not receive data from client: Connection reset by peer 检查代理、负载均衡器或防火墙
客户端 keepalive 判断失效链路不可用 这次测试未读取服务端日志 见下文

表中的原因和日志行来自实测；处理建议是我们的建议，除非下文明确说明也做过测试。如果这句话出现在建立连接阶段，原因又有所不同，我们在《连接被拒绝：服务器在运行吗？》中讨论过：有东西接受了连接，在我们的例子里是 Docker 的端口映射，但它后面没有运行中的数据库服务器。

2026 年 10 月 30 日至 31 日夜间，我们在官方 postgres Docker 镜像 13.23、15.19、17.11 和 18.6 上进行了测试，并在当晚稍后使用文末脚本重复了大多数场景。客户端为 psql 17.11、psycopg2 2.9.13、psycopg 3.3.6、pgJDBC 42.7.13、node-postgres 8.23.1 和 pgx 5.11.0，另外还使用了 SQLAlchemy 2.1.6 与 PgBouncer 1.26.0。正文未标注版本的结果来自 17.11。

这句话在 libpq 中有五处产生位置，服务端没有。在其中一处，即读取返回 0 字节的位置，源码认为“连接已经关闭”，接着 libpq 输出 This probably means the server terminated abnormally，意思是“这可能意味着服务器异常终止”。这个推测可能不成立，下文的网络重置场景就是例子。在这条消息里，“server”只是指套接字的另一端。

怎样找到真正的原因？

先看客户端在这句话之前输出了什么。FATAL 表示服务端或连接池代理说明了原因。WARNING 表示会话是受其他事件影响而终止的：另一个后端崩溃、执行了立即关闭，或者等待同步备库的操作被取消。前面没有消息也说明不了多少，因为我们测试的 psycopg2 和其他客户端库并没有显示这些消息。

然后查看对应时刻附近的服务端日志。搜索 was terminated by signal，不要只搜 server process：PostgreSQL 18 在这里写的是 client backend (PID ...)，13、15 和 17 写的才是 server process (PID ...)。

如果你的会话只是受牵连的一方，客户端会收到一条警告。psql 会输出它，而我们测试的客户端库不会。对一个后端执行 kill -9，会让服务端终止所有会话：

TEXT
WARNING:  terminating connection because of crash of another server proc...
DETAIL:  The postmaster has commanded this server process to roll back t...
HINT:  In a moment you should be able to reconnect to the database ...
server closed the connection unexpectedly

随后日志会显示恢复过程。在空数据库中，从杀进程到出现 database system is ready to accept connections，大约花了 150 毫秒。这个数字不能说明有实际 WAL 需要回放时的恢复时间。如果需要回放 WAL，日志会出现 redo starts 和 redo done，而不是 redo is not required。

TEXT
LOG:  server process (PID 240) was terminated by signal 9: Killed
DETAIL:  Failed process was running: set application_name=victim; select ...
LOG:  terminating any other active server processes
LOG:  all server processes terminated; reinitializing
LOG:  database system was interrupted; last known up at 2026-10-30 22:54...
LOG:  database system was not properly shut down; automatic recovery in ...
LOG:  redo is not required
LOG:  database system is ready to accept connections

这条警告有 SQLSTATE 57P02，但你无法把它作为异常捕获。它以通知消息的形式到达客户端，随后连接结束。在 psycopg 3 中，notice handler 收到了 57P02，异常本身却没有 SQLSTATE。15、17 和 18 只把这条警告发给客户端；13 还会为每个会话记录日志。

从 15 开始，立即关闭有了自己的措辞：terminating connection due to immediate shutdown command。13 则报告另一个进程崩溃，尽管并没有发生这样的崩溃。

为什么 psycopg2 显示的信息比 psql 少？

因为同一个事件在不同客户端中的表现不同。使用当前的 psycopg2 时，服务端给出的原因不会传递到你的代码中：

客户端 pg_terminate_backend() 对后端执行 kill -9 下一次查询
psql FATAL: terminating connection...，随后是 server closed... server closed... 非交互模式下停止，退出码为 2
psycopg2 2.9.13 server closed...，pgcode 为 None server closed...，pgcode 为 None connection already closed
psycopg 3.3.6 AdminShutdown，57P01 consuming input failed: server closed... the connection is closed
pgJDBC 42.7.13 FATAL: terminating connection...，57P01 08006，An I/O error occurred while sending to the backend. 08003，This connection has been closed.
node-postgres 8.23.1 空闲时触发带有 57P01 的 'error' 事件；执行中则查询以 57P01 拒绝 'error' 事件，Connection terminated unexpectedly Client has encountered a connection error and is not queryable
pgx 5.11.0 FATAL: terminating connection... (SQLSTATE 57P01) conn closed，或查询中出现 unexpected EOF conn closed

pg_terminate_backend() 这一列在 13、15、17 和 18 上的结果相同。不论会话空闲还是正在执行查询，psycopg2 都只给出那一句话。因此，通过 psycopg2 观察时，57P01、超时和崩溃看起来都一样，只有服务端日志能区分它们。

这个行为取决于 psycopg2 的 wheel 包，以及包中自带的 libpq。网上一些较早的回答能在文本中看到服务端原因，当时确实如此。我们在 17.11 上使用四个 wheel 包终止了相同的会话：

psycopg2-binary 自带 libpq 异常 pgcode 消息中是否包含服务端原因
2.8.6 11.5 AdminShutdown 57P01 是
2.9.3 14.1 OperationalError None 是
2.9.9 16.0 OperationalError None 否
2.9.13 17.11 OperationalError None 否

因此，捕获 psycopg2.errors.AdminShutdown 的代码可能在一次版本升级后不再触发，而这个变化本身不会报错。每一行中，空闲会话与正在运行的会话表现相同。如果日志里只有上一张表最后一列的消息，例如 connection already closed，那是后续错误，应该往前寻找最初的错误。

为什么直到下一次查询才报错？

因为客户端空闲时没有读取套接字。设置 idle_session_timeout = 2s 后，服务端在 2 秒后关闭了会话，但 psql、psycopg2、psycopg 3、pgJDBC 和 pgx 都直到下一次查询才发现。因此，如果应用等待了十分钟，错误会出现在一条普通的 SELECT 上，此时实际超时早已发生。

idle_in_transaction_session_timeout 和 transaction_timeout 的表现相同。13 中没有 idle_session_timeout，会报 unrecognized configuration parameter；15、17 和 18 中可以使用。

node-postgres 是例外：它持续读取，因此即使没有查询正在运行，也会收到 'error' 事件。如果没有监听器，这个事件会终止进程：

TEXT
node:events:502
      throw er; // Unhandled 'error' event
error: terminating connection due to administrator command

Client 和 Pool 都是如此。添加 pool.on('error', ...) 后，连接池完成清理，下一次 pool.query 可以正常执行。

文档对 idle_session_timeout 有这样的提醒：“对连接池软件或其他中间件建立的连接启用此超时应当谨慎，因为这一层可能无法妥善处理意外关闭的连接。”

是 OOM killer 吗？

PostgreSQL 不会直接告诉你。我们实际触发了一次：容器设置为 --memory=300m --memory-swap=300m，work_mem = 2GB，并对 3000 万行数据排序。客户端得到了那句普通的断连提示。日志与手工执行 kill -9 相同，DETAIL 中指出了排序查询：

TEXT
LOG:  server process (PID 66) was terminated by signal 9: Killed
DETAIL:  Failed process was running: select count(*) from (select g, md5...
LOG:  terminating any other active server processes

证据在 PostgreSQL 之外：docker inspect 显示 OOMKilled=true、Running=true。容器仍在运行，因为只有一个后端进程被杀，postmaster 重启了其余进程。只统计容器重启次数的监控看不到这种情况。

还可以检查 dmesg 和 kubectl describe，不过我们没有测试这两种方式。文档对 OOM killer 的建议是设置 vm.overcommit_memory=2，以“显著降低发生的概率”。这个宿主机级设置针对内核的全局 OOM killer，无法避免我们测试中这种由容器内存上限引发的问题；对于这种情况，处理方法是减小 work_mem 或提高内存上限。

服务端什么都没做，为什么也会出现？

有两种情况。在网络重置测试中，服务端日志一直为空，因为只有客户端收到了重置。

来自网络的重置。 我们让服务器自身的网络协议栈用 TCP reset 响应，而 PostgreSQL 持续运行。libpq 把 ECONNRESET 转换成了同一句话：

TEXT
[psql]     server closed the connection unexpectedly
[psycopg3] consuming input failed: server closed the connection unexpect...
[pgjdbc]   08006 An I/O error occurred while sending to the backend. cau...
[node-pg]  read ECONNRESET
[pgx]      conn closed

这里的 This probably means the server terminated abnormally 显然判断错了。只有 pgJDBC 和 node-postgres 指出了连接重置。

链路失效与客户端 keepalive。 我们丢弃所有数据包，模拟 NAT 表遗忘连接后的行为，并把 keepalive 设置为：空闲 3 秒开始探测，探测间隔 1 秒，探测 3 次。如果 10 秒后才发起查询，它会立刻报 server closed the connection unexpectedly，而服务端运行正常。我们的理解是，keepalive 已经提前关闭了套接字。因此，如果启用 keepalive 后，这条消息出现得更频繁，你看到的可能是原来长时间挂起的请求现在更快地失败了。

并非每个网络问题都会产生错误。我们把服务器从 Docker 网络断开 35 秒，客户端只是等待；等 TCP 重传成功后，查询在 52.75 秒时成功返回。

如果连接一直挂起而没有报错呢？

如果链路静默失效，没有 reset，很长时间都不会报错。我们使用 psycopg2 连接一个正常运行的服务器，并丢弃双向数据包：

链路失效时的状态 客户端设置 结果
空闲，1 秒后查询 keepalive 3/1/3 挂起，45 秒时停止观察
空闲，10 秒后查询 keepalive 3/1/3 立即报 server closed the connection unexpectedly
空闲，1 秒后查询 tcp_user_timeout=5000 5.44 秒后报 could not receive data from server: Connection timed out
空闲，10 秒后查询 tcp_user_timeout=5000 5.47 秒后报同样的错误
查询正在运行 未设置 挂起，45 秒时停止观察
查询正在运行 keepalive 3/1/3 6.13 秒后报 could not receive data...
查询正在运行 tcp_user_timeout=5000 挂起，45 秒时停止观察
查询正在运行 两者都设置 5.11 秒后报 could not receive data...

两项设置都需要。刚发出的查询尚未得到 TCP 确认时，keepalive 没有触发；查询已经得到确认、客户端只是在等待响应时，tcp_user_timeout 没有触发。这是我们的解释；表格中的结果来自实测。

不做任何设置时，需要很长时间。在 Linux 的 tcp_retries2=15 下，六种客户端使用空闲连接，并在链路失效 1 秒后发送查询，都在大约 951 秒、接近 16 分钟后失败。它们没有一个输出本文讨论的那句话：libpq 输出 could not receive data from server: Connection timed out，node-postgres 输出 read ETIMEDOUT，pgJDBC 给出 08006，pgx 输出 unexpected EOF。libpq 文档说 keepalive 默认开启，但内核默认空闲时间为 7200 秒，这意味着第一次探测要等两个小时。

服务端也有同样的问题。当正在执行查询时，客户端所在方向变成网络黑洞，仅设置 client_connection_check_interval = 1s 没有作用：25 秒后停止观察时，后端仍然存在。再加上服务端 keepalive 3/1/3 后，后端大约 6 秒后退出，报 FATAL: connection to client lost。默认情况下，断连后的空闲后端在整个观察期间，即 45 秒内一直存在。它还占着连接槽位，积累起来就可能触发 remaining connection slots are reserved。

pool_pre_ping 能解决吗？

大多数情况下可以，但有两个缺口。我们使用大小为 3 的 SQLAlchemy 连接池，通过 pg_terminate_backend() 杀掉其中所有连接，分别测试 psycopg2 和 psycopg 3；还通过 docker restart 测试了 psycopg2。随后串行发起五次请求。

启用 pool_pre_ping 后，五次都成功。没有启用时，第一次请求报 OperationalError ... server closed...，psycopg 3 则报 AdminShutdown，后面四次成功。

因此，失败的恰好是一次请求，而不是三次。这符合 SQLAlchemy 在发现断连后使整个池中旧连接失效的规则。这是单线程测试，我们没有测试并行负载。

第一个缺口：pre-ping 只检查某一个时刻的状态。连接从池中取出后再断开，仍然会报 OperationalError ... server closed the connection unexpectedly。第二个缺口：遇到网络黑洞时，ping 本身也会挂起，我们等待 30 秒，没有任何请求返回。添加 connect_args=dict(tcp_user_timeout=3000) 后，第一次请求在 6.49 秒后失败，第二次在 3.01 秒后失败。因此，pre-ping 还需要底层超时设置。

中间加入 PgBouncer 1.26.0 后，消息里的“server”就是连接池代理。设置 client_idle_timeout = 2，psql 会在那句话前输出 FATAL: client_idle_timeout；psycopg2 只输出那句话；psycopg 3 和 pgx 给出 08P01，即 protocol_violation，尽管协议本身并没有出错。node-postgres 以事件形式收到了同样的错误码；pgJDBC 最后启动，没有达到超时。对于 server_lifetime，在客户端空闲且没有查询运行的测试中，我们没有看到消息。

我的 COMMIT 到底成功了吗？

仅凭这个错误，客户端无法知道。我们让 COMMIT 停在指定位置，然后在提交记录写入之前，或者提交记录刷盘之后，杀死后端。

提交记录写入之前被杀

  1. 客户端发送 COMMIT 并等待，事务仍然打开。
  2. 后端在写入提交记录前被杀，WAL 中没有提交记录。
  3. 客户端收到 server closed...；恢复后，表中有 0 行。

提交记录刷盘之后被杀

  1. 客户端发送 COMMIT 并等待，事务仍然打开。
  2. 后端刷出提交记录，在返回响应前被杀；提交记录已经在磁盘上。
  3. 客户端收到相同的 server closed...；恢复后，表中有 1 行。

行数与客户端消息在 17 和 18 上均做了测量；其他客户端的结果如下：

项目或客户端 提交记录写入前执行 kill -9 刷盘后执行 kill -9
恢复后行数 0 1
psql、psycopg2 server closed... server closed...
psycopg 3 consuming input failed: server closed... 相同
pgJDBC 08006，An I/O error... 相同
node-postgres Connection terminated unexpectedly 相同
pgx conn closed 相同

在 17 和 18 上，输出相同，结果却相反。使用 pg_terminate_backend() 时，各客户端的输出有所区别，但 psycopg2 仍然在两种结果下输出同一句话。

网络中断时也一样：设置 tcp_user_timeout=3000，无论丢失的是响应还是 COMMIT 请求本身，3.42 秒后都得到 could not receive data from server: Connection timed out。前一种情况表中有那一行，后一种情况没有。后一种情况下，后端还留在服务端，处于 idle in transaction。

在频繁提交的循环中，这种情况很常见。我们用 psycopg2 循环执行自动提交的 INSERT，并大约每 0.9 秒在随机时刻向后端发送 kill -9，直到有 100 条语句失败：

synchronous_commit 失败的语句数 报失败，但数据行存在 已确认成功，但数据行丢失
on 100 77 214,597 次中为 0
off 100 0 1,824,920 次中有 197,385 次

盲目重试那 77 次操作，会写入重复数据或触发唯一约束冲突。第二轮测试中，100 次失败有 81 次实际写入，210,747 次确认成功的操作没有丢失数据。这个数字属于这组逐行提交的循环；它说明这种情况会发生，并不能说明它在你的系统中发生的频率。off 那一行展示了另一面：报错时确实没有写入，但返回成功却不代表数据最终保留下来。

事务状态也说明了这一点：失败后，psycopg 3 的 info.transaction_status 为 UNKNOWN，psycopg2 中对应值为 4，与其他失效连接一样。SQLSTATE 中虽然存在 08007 transaction_resolution_unknown，但没有客户端向我们返回这个代码。对于一个实际已经写入数据的 COMMIT，pgx 5.11.0 在 conn closed 错误上把 SafeToRetry 报告为 true，因此不能仅凭这个标志决定重试 COMMIT。

pg_xact_status 能告诉我吗？

崩溃后未必可靠。文档列出了这个用途：“在 COMMIT 执行期间，应用与数据库服务器的连接断开后，确定事务究竟已经提交还是中止。”在 pg_terminate_backend() 之后，以及提交记录已经落盘后再杀进程的情况下，它可以正常工作。

在 COMMIT 期间、提交记录写入前执行 kill -9 后，我们查询自己事务 xid 的状态，让另一个会话执行一个事务，再次查询。下面是 17.11 中的一轮结果：

TEXT
r1 xid=763 right-after='ERROR:  transaction ID 763 is in the future' ...

另一个会话获得了相同的 xid，随后 pg_xact_status 返回 committed，但我们原来写入的数据行已经不存在。第一次运行的 8 轮中出现了 6 次，第二次运行的 8 轮全部出现。其余两轮返回 aborted，这是正确的。

我们的解释是，这个 xid 对应的 WAL 尚未离开 PostgreSQL 的缓冲区，因此恢复过程不知道它已被分配，又把它分配了一次。在一次重新核查的 xid 复用中，WAL 里只有另一个会话的记录。如果 WAL 已经先写出，例如被另一个事务的提交带出，状态就是正确的，后续分配的 xid 也会继续递增。对于未结束的事务，我们在 18 上也观察到同样的情况，2 次中出现 2 次；13 上则是 2 次中出现 1 次。

有负载时结果也没有更好。四个会话持续提交，每轮触发 15 次崩溃，两轮中分别有 33 个中的 18 个、39 个中的 9 个具有已知 xid 的中断事务，最终被报告为 committed，但它们的数据行已经消失。刚恢复时，这些事务会报 transaction ID ... is in the future，直到另一个会话获得该 xid。函数文档没有提到这一点。这可能是已知行为，我们尚未向 PostgreSQL 开发者询问。

真正有效的是使用自己的标识：在同一个事务中写入一个唯一值，失败后重新连接并查找它；如果旧后端可能仍然活着，就改用 insert ... on conflict do nothing 重试。上面的循环就是用这种方式统计出那 77 次的。

为什么粘贴到 psql 的脚本只执行了一部分？

因为交互式 psql 会重新连接并继续执行。我们在事务中途终止了会话：

PSQL
postgres=*# insert into y values(2);
FATAL:  terminating connection due to administrator command
server closed the connection unexpectedly
The connection to the server was lost. Attempting reset: Succeeded.
postgres=# insert into y values(3);
INSERT 0 1
postgres=# commit;
WARNING:  there is no transaction in progress
COMMIT

最后表里只有 3：值为 1 的行被回滚，写入 2 的语句没有执行，写入 3 的语句在显式事务之外执行了。提示符也说明了这一点：=*# 变成了 =#。非交互式 psql 会停止并以退出码 2 退出，文档对此的描述是“与服务器的连接失效，且会话处于非交互模式”。

这个错误还有哪些不同措辞？

启用 SSL 时，连接关闭通常有其他措辞，而且措辞取决于客户端的 libpq，而非服务端。在 sslmode=require 下，TCP reset 仍然给出了本文讨论的普通提示。这个结果来自 psql 和 psycopg2，使用 libpq 17.11，于 11 月 2 日重新核查：

事件，sslmode=require libpq 17.11（psql、psycopg2） libpq 18.6（psycopg 3、镜像中的 psql）
kill -9 SSL SYSCALL error: EOF detected SSL error: unexpected eof while reading
pg_terminate_backend() SSL connection has been closed unexpectedly，psql 还会加上 FATAL psycopg 3：AdminShutdown，57P01

其他形式包括：consuming input failed: server closed... 来自 psycopg 3。在 COPY 期间，pg_dump 会输出 Dumping the contents of table "big" failed: PQgetCopyData() failed.，然后在 Error message from server: 下方显示那句断连提示；Command was: 一行说明了中断的位置。

connection to server at ..., port 5432 failed: server closed... 则发生在建立连接阶段。我们在《no pg_hba.conf entry for host》中讨论过：在 Docker 端口映射后面，listen_addresses 配置可以导致这种现象。服务端实际会发送哪些错误码，可以参见原站的 SQLSTATE 实测汇总。

复现方法

原文附有三个脚本：setup.sh 在私有 Docker 网络中启动数据库服务器，并为每种客户端技术栈启动一个容器，测试密码为 test；run.sh 输出前面列出的主要客户端消息与日志行。

运行 PREFIX=pgclosed ./setup.sh，然后运行 PREFIX=pgclosed ./run.sh 2>&1 | tee results.txt。./run.sh long 增加持续 16 分钟的网络黑洞测试，./setup.sh clean 删除测试环境。xid-load.sh 独立执行负载下的 pg_xact_status 测试，命令为 PREFIX=pgclosed ./xid-load.sh。竞争条件和耗时数字会因你的环境而异。

脚本覆盖主要场景，并未包含全部场景。未包含的内容有：SSL、pg_dump、交互式 psql、docker network disconnect、docker restart、18 上的 COMMIT 测试，以及使用 psql、psycopg 3、pgJDBC 和 node-postgres 的 COMMIT 测试；网络中断期间的 COMMIT 场景；13 和 18 上针对未结束事务的 pg_xact_status 测试；连接取出后断开时的 pre-ping 缺口；PgBouncer 被杀及 server_lifetime；node-postgres 的 Pool；以及 57P02 的 notice handler。

我们没有测量的内容

PostgreSQL 14、16，以及 12 和更早的版本。Patroni、RDS 或 Render 的故障切换，以及已经确认的 COMMIT 能否在故障切换后保留。具有空闲超时的真实代理，例如 AWS NLB、RDS Proxy、Azure 负载均衡器，以及 Kubernetes conntrack；我们的网络黑洞使用 iptables 模拟。

其他未测项目包括：完整等待两个小时的默认 keepalive 配置；结合副本使用 pg_xact_status；pgJDBC 的 socketTimeout；HikariCP；node-postgres 的 keepAlive；pgxpool；Django、Rails、PHP PDO（General error: 7）、asyncpg、pgAdmin 和 Supabase；psql 的 ON_ERROR_STOP；SQLAlchemy 并行负载及 pool_recycle；pg_ctl stop -m smart。我们也没有确定究竟是哪一个 libpq 版本使 psycopg2 不再输出 FATAL：测试对象是 wheel 包，没有独立测试 libpq。
