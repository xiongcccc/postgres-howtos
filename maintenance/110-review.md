## 技术核对

- PostgreSQL 18 查询规划参数、release-18，以及本地禁用方法实验：禁用是规划偏好和约束，不保证某类节点绝对消失。18 开始独立统计 disabled nodes；无可用索引的堆表仍 Seq Scan，显示 Disabled: true。
- 未沿用幻灯片“规划器尝试所有组合”的简化；正文只说明估算、候选路径与选择。未把 cost 当成毫秒，亦未把多次索引查找示意写成实测压测结果。
- 幻灯片早期版本惩罚数值标成 10M，而同页计划显示 10000000000；正文不扩展这个历史数值，采用 PG18 当前机制和输出。
- pg_hint_plan REL18_1_8_1 官方源码、PG18 分支文档：模块加载与 CREATE EXTENSION 建表分开；别名优先、提示表优先于注释、query_id 与 application_name 作用范围。表的匹配条件和优先级另查 get_hints_from_table。
- 扩展主版本绑定，PG18 分支版本 1.8.1；DisableIndex 仅按 PG18+ 分支说明。不把 PG19 模块语法当作所有版本都支持的通用 SQL 提示。
- pg_plan_advice 官方文档与 19rc1 实验：PLAN_ADVICE 生成字符串；匹配目标与最终执行符合是不同检查；missing_idx 反馈实际为 matched, inapplicable, failed，默认真实索引仍可作为合法计划。
- 原 PDF 第 38 页将反馈概括成 applied / cannot be applied；正文按官方定义和实测细化，避免仅看 matched 就宣称约束已成功。未声称出现无效 advice 就抛错或必定回退到某一种节点。
- pg_hint_plan HashJoin(a b) 是关系集合；native HASH_JOIN(b) 是将目标放在内侧。JOIN_ORDER、子查询目标和复杂连接约束不以改标签大小写冒充迁移兼容。
- pg_stash_advice 使用动态共享内存、命名 stash、query ID 映射和可选文件持久化；preload、后台 worker 与正常停止保存按文档/实测确认。正文不把异常退出前未落盘内容当作持久化，也不承诺缓存计划自动失效。
- 截至核对日期，官方版本页面仍列 PG19 为开发版本，并提供 2026-10-15 的 RC1 公告。候选版本信息集中记录在元数据，不在正文重复插入版本声明。

## 隔离实验

```sh
python3 maintenance/110-verify.py \
  --pg18-bin /opt/homebrew/opt/postgresql@18/bin \
  --pg19-bin /tmp/howto110-build/pg19/bin \
  --hint-build /tmp/howto110-build/pg_hint_plan-REL18_1_8_1 \
  --check-output
```

- PG18 使用已有 Homebrew 18.4；扩展从官方 tag REL18_1_8_1 编译，未安装到 Homebrew 或系统目录。验证脚本把 control 和 SQL 复制到临时 extension_control_path，并将 dynamic_library_path 指向编译目录；兼容 .so / .dylib。
- PG19 从官方 postgresql-19rc1.tar.bz2 编译到 /tmp，构建 pg_plan_advice 与 pg_stash_advice。SHA-256 与官方校验文件一致：af105fc8e960fc836a09fc2cd7f582b49fd17675d9d36631abe3a565bfd7d701。
- pg_hint_plan 的官方 tag 归档 SHA-256：a4fca485e54fe8e67f9104595ab254aee17cf766d0f261666f5079965d225f6a。此为下载产物记录，不伪称独立签名校验。
- 两个 UTF8、无 locale 的临时实例分别使用私有 Unix socket、shared_buffers=32MB、max_connections=10；listen_addresses 为空。不访问已有数据库，不开放 TCP。
- PG19 仅在自己的临时启动选项中预加载两个模块。脚本在成功和异常退出路径关闭会话、停止实例、删除临时数据目录；正常重启测试也只操作自己创建的实例。
- 修订后直接提取正文 10 个具名 SQL 块，PG18/19 各执行公共的建表、索引基线与规划开关，再按扩展分支执行。辅助边界检查、query ID 动态读取及清理由脚本提供，不要求在正文完整呈现验证流程。验证脚本仅用 Python 标准库。

修订后重新执行 `--check-output`，完整机制与清理检查通过，逐一对照正文六组结果：

- 两版本的公共步骤输出一致。主键点查为 Index Scan，actual rows=1.00、Index Searches=1；禁用索引/位图后变为 Seq Scan，实际过滤 19999 行；事务回滚后开关恢复 on。
- 没有索引的 heap_only 在禁用 Seq Scan 后仍使用该节点，显示 Disabled: true。
- `SeqScan(i)` 改变实际访问方法；`SeqScan(items)` 因别名不匹配，仍用 items_pkey。
- 提示表按动态读取的 query ID 和 howto110 应用名配置；表中 SeqScan(i) 覆盖注释里的 IndexScan，删除规则后索引计划恢复。
- 额外检查相同结构的 id=43 也命中为 id=42 配置的规则；换成 other_application 后不命中，恢复 Index Scan。没有硬编码任何一次运行的 query ID。
- PG19 输出 INDEX_SCAN 和 NO_GATHER advice；SET LOCAL SEQ_SCAN 后显示 matched，回滚撤销局部设置。
- missing_idx 仍允许产生合法的真实索引计划，但指定要求报告 matched, inapplicable, failed；本文展示的是本例实际结果，不声称所有无效 advice 都采取同一种回退。
- stash 在原连接、新连接，以及正常停止并重启后均产生 SEQ_SCAN(i) matched。正常停止时确认存在 pg_stash_advice.tsv，重启读取后仍生效。
- 清理前确认 stash 从共享存储消失，随后删除扩展及测试 schema；两个实例最后均无 hint_demo。脚本的维护检查先于扩展删除，避免把已删除 SQL 函数误作产品行为失败。

验证范围为上述计划选择、规则范围与优先级、反馈和正常重启持久化；连接方法/Rows 提示表是按官方文档说明，没有宣称做了连接负载压测或原 OMDB 性能复现，也没有执行异常退出持久化测试。

## 读者视角复核

- 开头围绕执行计划变化后如何验证替代方案，不从模块名称或语法列表开始；解释估计行数与连接次数的关系，再用可执行例子说明干预的后果。
- 选择主键点查并刻意改成全表扫描，让读者能看懂返回一行却过滤 19999 行的差别，不用机器相关的毫秒数推导“提示让查询更快”。
- 从局部规划开关，到表别名的精确目标，再到按 query ID 管理，范围逐步扩大；提示表优先级和常量归一化说明了实际运维中容易遗漏的作用范围。
- PG19 不只给出模块名称：展示生成 advice、事务内应用、无效索引反馈、按查询保存，以及跨连接/重启的条件。解释约束候选路径，不等于保存不可变执行计划。
- 正文保留最小表结构和数据生成方式、关键查询与输出。query ID 说明获取方式，以 psql 变量引用当前值；自动提取、额外匹配测试、重启测试与清理留在维护脚本中。
- 建议围绕具体判断：估计与实际行数差距、替代路径实际表现、代表参数、规则作用范围和撤销条件。避免只说“结合业务评估”，也不鼓励为单条 SQL 全局禁用一种连接方法。
- 校订细节仅在维护记录中，正文不把幻灯片错误逐条列成审核报告。官方链接集中于文末，未使用“讲者”“先把……说具体”“反直觉”等模板语气，也没有虚构亲历事故。
