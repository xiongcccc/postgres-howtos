## 隔离实验

环境：PostgreSQL 18.4（Homebrew）、macOS / aarch64、UTF-8。脚本：`maintenance/104-verify.py`。

```sh
python3 maintenance/104-verify.py
# 安装位置不同时：
python3 maintenance/104-verify.py --pg-bin /path/to/postgresql18/bin
```

脚本只依赖 Python 标准库和 PostgreSQL 工具。临时数据目录与 Unix socket 每次单独生成，不监听 TCP，不连接已有数据库；保留默认同步提交和 fsync。会话带语句超时与事务空闲超时，用观察会话确认阻塞状态后再释放锁，不依赖固定 sleep 猜测并发时序。结束时关闭会话、停止实例并删除临时目录。

### 同行更新

每轮余额重置为 100，B 建立快照，A 扣除 70 未提交，B 尝试在余额 >= 50 时扣除 50。观察结果：

- A：`idle in transaction`，`Client / ClientRead`。
- B：`Lock / transactionid`，`pg_blocking_pids()` 精确指向 A。
- A 提交后：RC 更新 0 行，余额 30；RR 和 Serializable 返回 SQLSTATE 40001，回滚 B 后余额仍为 30。
- 补充对照：A 仅 `SELECT FOR UPDATE` 而不修改，B 使用 RR；A 提交后 B 的更新成功，余额 50。区分“锁冲突”与“快照后的修改冲突”。

### 写偏差

航班容量为 2，订单表初始为空。两个事务分别读取剩余量为 2，各插入不同订单、数量 2，再依次提交：

| 隔离级别 | 提交结果 | 最终订出数量 |
| --- | --- | --- |
| READ COMMITTED | 两个成功 | 4 |
| REPEATABLE READ | 两个成功 | 4 |
| SERIALIZABLE | A 成功，B 的 COMMIT 返回 40001 | 2 |

实验是控制时序的最小写偏差例子，没有压测 SSI 重试吞吐。Serializable 错误可能随实际执行顺序在语句或提交阶段触发，不把本次触发时点泛化。

### 正文 SQL 与函数

脚本提取正文八个 SQL 块，在相应会话和正确顺序下执行；诊断查询在阻塞发生时运行，包含 A/B 的实际 PID。正文扣减实验结束后余额 30，函数扣减 10 返回 20。

额外核对函数：

- 外层显式事务内调用返回后，其他会话仍被阻塞，提交后才推进。
- 独立调用完成后，其他会话的更新能够完成。
- 余额不足或账户不存在返回 P0001，金额为 0、负数或 NULL 返回 22023；失败不会改变余额。
